# NOTICE-276–280 — Quiet hours for edited delivered-order business notifications

**Approved requirement:** Admin may edit a delivered order at any time. When the edit is saved from **20:00 until before 08:00 Asia/Ho_Chi_Minh**, the customer must **not** receive the edit notification during those quiet hours. Publish it on or after **08:05 VN** instead, avoiding repeated corrections to the same order in a single night.

## Given / When / Then

- **Given** an enabled global business-notification switch, enabled `order_edit` type, and opted-in customer; **when** an admin meaningfully edits a delivered order at 20:00–07:59 VN; **then** the order, items, and financial ledger commit immediately, while the notification is retained privately until 08:05 or a later daytime retry.
- **Given** several night edits of one delivered order; **when** the edit is repeated before morning; **then** the queue replaces the earlier snapshot and releases at most **one** latest message for that order and morning. A meaningful daytime edit supersedes a pending nighttime one.
- **Given** a queued notice; **when** the customer opts out, sender/account becomes invalid, or order changes customer/status before dispatch; **then** no message is released.
- **Given** a genuine portrait PNG generated by the existing TAPHOA client; **when** the edit occurs at night; **then** the PNG can be staged in private `v21-media` Storage with authenticated ownership, MIME/size checks, and the linked customer's conversation. No Chat message/Zalo outbox/media record is created at night. The dispatcher inserts a single Chat text+PNG message at release. If the PNG cannot be completed after a bounded 15-minute grace period, send text and the canonical customer order link rather than blocking indefinitely.
- **Given** a new order, draft→delivered conversion, finance collection/debt notice, manual Chat message, or a no-op edit; **when** any occurs; **then** its pre-existing business behavior remains unchanged (no-op edits still produce no notice).
- **Given** an edit notification already delivered before rollout; **when** migration is applied; **then** do **not** queue/re-send it.

## Runtime owners and controls

- **Backend owner:** `public.taphoa_chat_notify_customer` before `v21_messages` insert, only on `taphoa:%:order-edit`. No changes to `public.taphoa_save_order` order/ledger logic.
- **Queue and image owner:** `v21_private.taphoa_order_edit_quiet_queue`, `public.taphoa_order_notice_image_ticket`, `public.taphoa_order_notice_image_attach`, and `v21_storage_private.can_upload_taphoa_order_notice`. The private table and dispatcher are revoked from `anon/authenticated`; the existing authenticated admin image-ticket RPCs keep their original ACL.
- **Morning owner:** private `v21_private.taphoa_order_edit_quiet_dispatch()` through `cron.job` `taphoa-order-edit-after-0805-vn` at `5,15,25,35,45,55 1-12 * * *` UTC. Cron retries only during 08:05–19:55 VN; 25 rows maximum per run; `FOR UPDATE SKIP LOCKED`; existing Chat/Zalo push and media owner unchanged.
- **Idempotency:** one row per `(order_id,dispatch_date_vn)`, latest `client_id`, deduplication on `v21_messages(sender_account_id,client_id)`. Worker source permission and customer opt-in are rechecked before publication.
- **Resource impact:** one private queue record per edited order/morning, no overnight client polling, no new HTTP sender, no extra Zalo before the release window. Images are uploaded only by the pre-existing on-save portrait renderer.
