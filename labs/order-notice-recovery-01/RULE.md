# ORDER-NOTICE-RECOVERY-01
## Evidence and scope
- Incident 24 Nov 2026: delivered sale committed once; customer and staff empty-message tickets created. Customer Storage POST 200 and staff ObjectCreated, no matching attach request in the incident window; both objects absent at audit. 1 of 57 automatic customer order notices in seven-day audit lacks an image.
- No evidence proving the browser's exact interruption. Existing client awaits upload then attach, and a failed task is only console-logged; original ticket expires in 20 minutes. Empty message is intentional final image-only design but unsafe as a completion signal.
- This PR is an isolated candidate, not a production migration or a complete fix. Phase A covers customer create/deliver notices, using the command-log snapshot and exact original message. Staff and edited-order variants require independent recipient proof and remain pending.
## Parent contract
1. Database commit ACK and notice completion ACK are distinct. Never repeat save/deliver, insert a message, alter order data or ledger to repair media.
2. Recover by exact message ID, authenticated original admin, active customer opt-in, committed snapshot, matching current order revision and conversation. Reject deleted/reassigned/edited orders, foreign account, other media, conflicting ticket, or disabled recipient.
3. Ticket is durable. After expiry, existing valid Storage object is reused only after PNG signature, IHDR dimensions and exact length verification; missing object rotates asset ID so stale attachment cannot commit. Do not overwrite any object. Lock message and ticket for concurrent recovery. Active lease is not stolen.
4. Attachment wrapper rechecks order revision and recipient, uses existing attach RPC, confirms actual media + storage evidence; idempotent retry may only refer to same asset. No success from HTTP alone.
5. Next phase: server-authorized bounded pending listing, a recoverable worker (prefer server-side canonical renderer, or scoped foreground/resume client until server renderer passes), stage-specific ACK/failure status, bounded retries and cleanup protection. Preserve image-only presentation. Never auto-send old messages without reviewed eligibility. No customer data in test fixture or repository.
6. Before release: isolated PG fixture + concurrent and privilege tests, compare actual deployed attach and Zalo enqueue behavior, verify image rendering matches the existing canonical portrait, browser interruption/reconnect tests, and production read-only eligibility check. Then repair the original incident using existing message, compare ledger and message count before/after. No production writes by this PR.
